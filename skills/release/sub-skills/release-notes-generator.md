# DevAgent Sub-skill: Release Notes Generator
**Parent:** Release Orchestrator  
**Scope:** RELEASE-NOTES.md for this specific release  
**Output:** `RELEASE-NOTES.md`

---

## Purpose

Generate human-readable release notes for this specific version. Unlike the changelog (which is a technical record), release notes are written for the end user — clear, concise, and focused on value delivered.

---

## Required Inputs

| Input | Source | Required |
|-------|--------|----------|
| PRD.md | docs/PRD.md | Yes |
| Plan.md | docs/Plan.md | Yes |
| VV-Report.md | docs/VV-Report.md | Yes |
| Maintenance input queue | state/maintenance/input-queue.md | If exists |
| Version string | Orchestrator | Yes |
| Project name | PRD.md overview | Yes |

---

## 1. Release Notes Structure

```markdown
# Release Notes — {Project Name} v{version}
**Release Date:** {YYYY-MM-DD}  
**Version:** v{version}  

---

## What's New
{1-3 sentence summary of the most important changes in plain language}

## New Features
{For each new feature — one paragraph, user-facing language, no technical jargon}
**{Feature Name}**  
{What it does and why it matters to the user}

## Bug Fixes
{For each resolved bug — one line, user-facing description}
- Fixed: {what was broken and now works}

## Known Issues
{List any open structural bugs from maintenance queue}
- {BUG-XXX}: {description} — {workaround if available}

## NFR Manual Verification Pending
{List any NFRs pending manual sign-off from NFR-Checklist.md}
- {NFR-XXX}: {description} — awaiting manual verification

## Upgrade Notes
{Any breaking changes, migration steps, or configuration changes required}
{If none: "No breaking changes in this release."}

## Requirements Delivered
| Feature ID | Feature Name | Status |
|------------|-------------|--------|
| FEAT-001 | {name} | ✓ Complete |

---
*Generated by Release Skill v{skill-version}*
```

---

## 2. Writing Rules

- Write for a technical user who uses the software, not the developer
- Avoid: requirement IDs, design element IDs, internal jargon
- Include: FEAT IDs and BUG IDs in brackets for traceability, but explain in plain language
- Known issues section is mandatory — write "None" if clean
- Upgrade notes section is mandatory — write "No breaking changes" if clean

---

## 4. Output

Write to `RELEASE-NOTES.md` in project root.
Overwrite on each release — this file always reflects the latest release only.
Archive previous release notes to `docs/release-history/v{previous-version}-release-notes.md` if file already exists.
